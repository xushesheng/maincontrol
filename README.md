# zhukong

这是一个面向 Zynq AMP 场景的主控侧跨核通信工程。当前仓库聚焦 Linux 主控侧实现，按驱动侧与用户态侧拆分为两个目录：

- `amp_driver/`：Linux 内核侧 AMP IPC 驱动，负责 `/dev/amp_ipi` 接口、共享内存与寄存器映射、SGI 中断收发，以及 CPU0 与 CPU1 之间的数据搬运。
- `amp_user/`：Linux 用户态转发与控制程序，负责 `rf0` TUN 设备、静态节点表路由、业务数据聚合与转发、控制 UDP 报文抓取与下发。

当前仓库不包含 CPU1 配套程序、完整设备树节点和目标 BSP 工程，因此它描述的是主控侧实现，而不是一套可单独脱离目标板直接运行的完整系统。

## 根目录说明

- `AGENTS.md`：仓库内代理协作约束。
- `README.md`：项目说明。
- `宽带无线管理软件模块交换协议(v1.0).doc`：协议相关文档。

- `amp_driver/`：驱动侧源码与构建文件。

## 整体数据路径

### 业务数据路径

主控侧业务数据的典型路径如下：

1. 本地 PC 发往远端 PC 的 IPv4 包进入板卡 `eth1`。
2. 用户态程序通过 `proxy_arp`、`/32` 路由和 `rf0` TUN，把目标为对端 PC 的报文导入 `rf0`。
3. 用户态从 `rf0` 读取报文，对小包进行 `AMPB` 聚合，对大包直接发送，并通过 `/dev/amp_ipi` 写给驱动。
4. 驱动把数据写入 TX 共享区，填写目标 IP、节点号、长度等元数据，然后触发 CPU0 -> CPU1 的 SGI。
5. CPU1 返回的数据写入 RX 共享区后，通过 SGI 通知 CPU0。
6. 驱动把 RX 共享区数据搬入软件环形队列，用户态再从 `/dev/amp_ipi` 读出。
7. 用户态把解出的业务包重新写回 `rf0`，由内核继续路由到 `eth1` 发给本地 PC。

### 控制数据路径

控制数据不经过 `rf0`。用户态程序直接在 `eth1` 上抓取目标 UDP 端口 `3409` 的控制报文，校验控制帧格式后，通过 `/dev/amp_ipi` 发送给驱动，由驱动写入控制寄存器和控制参数区，再触发 SGI 通知 CPU1。

## 驱动侧目录 `amp_driver/`

### 文件说明

- `driver_main.c`
  - 提供 `/dev/amp_ipi` 的 `read()` 和 `write()` 接口。
  - 完成平台驱动的 `probe/remove`、misc 设备注册和 SGI 处理函数注册。
  - 当前版本在 TX 写路径上增加了互斥，避免并发写共享 TX 区。
- `driver_txrx.c`
  - 负责业务数据与控制数据的发送处理。
  - 维护 IP 与节点号映射关系。
  - 处理 CPU1 -> CPU0 的 RX 中断，并把接收数据写入驱动侧 RX 软件环形队列。
- `driver_map.c`
  - 负责共享内存、控制寄存器和监测寄存器的 `ioremap`、初始化和释放。
  - 当前版本在驱动侧维护 RX 环形队列及其统计变量。
- `driver_hardware.h`
  - 定义 TX/RX 共享区地址、控制寄存器地址、SGI 编号、跨文件共享变量和函数声明。
  - 定义驱动侧 RX 环形队列结构和深度。
- `driver_struct.h`
  - 定义控制帧结构和 `amp_net_msg` 数据结构。
- `Makefile`
  - 驱动侧模块构建文件，依赖外部内核源码树和交叉编译工具链。

### 当前驱动侧关键机制

- `/dev/amp_ipi` 是主控用户态与驱动交互的唯一设备接口。
- TX 共享区位于 `0x3800xxxx` 地址段，RX 共享区位于 `0x3900xxxx` 地址段。
- 业务数据和控制数据通过 `ctrl_reg` 区分：
  - `bit0` 表示业务数据。
  - `bit1` 表示控制数据。
- 当前 IP 到节点号映射规则为：
  - `192.168.1.10 ~ 192.168.1.42 -> node_id 0 ~ 32`
  - `239.0.0.1 -> 254`
  - `192.168.1.255 -> 255`
- 当前驱动 RX 路径已不是单包缓存，而是 `64` 深度的软件环形队列，用于降低用户态读取稍慢时的丢包风险。

## 用户态目录 `amp_user/`

### 文件说明

- `user_main.c`
  - 用户态主入口。
  - 打开 `/dev/amp_ipi`，创建 `rf0`，配置网关规则，并启动发送、接收和控制面线程。
- `user_datapath.c`
  - 实现 `rf0` TUN 创建与读写。
  - 实现业务数据发送、`AMPB` 聚合、单包直发和从驱动回读数据后的 TUN 回写。
  - 当前版本增加了统一的发送线程 `amp_tx_thread`，由它串行写 `/dev/amp_ipi`，避免业务流和控制流并发踩写。
- `user_control.c`
  - 使用 `pcap` 在 `eth1` 上抓取 UDP 端口 `3409` 的控制报文。
  - 校验控制帧头尾后，经统一发送队列转发给驱动。
- `user_gateway.c`
  - 负责根据本机 `eth1` 地址匹配节点表。
  - 配置 `rf0` 地址、`proxy_arp`、路由和相关 `sysctl`。
  - 定义当前三节点静态节点表。
- `user_struct.h`
  - 定义用户态 `amp_net_msg`、控制帧结构、`AMPB` 帧头和批次状态结构。
- `user_config.h`
  - 定义设备名、抓包接口、控制端口、批帧大小、聚合超时、发送队列深度、发送保护间隔和 `rf0` MTU。
- `user_declaration.h`
  - 汇总全局变量、发送队列结构、跨文件函数声明。
- `Makefile`
  - 用户态程序构建文件，输出目标为 `user_amp`。

### 当前用户态关键机制

#### 1. 静态三节点表

当前用户态内置了三节点静态节点表：

- 节点 `12`：板卡 `192.168.1.12`，本地 PC `192.168.1.22`，`rf0` 地址 `10.255.0.12/24`
- 节点 `13`：板卡 `192.168.1.13`，本地 PC `192.168.1.23`，`rf0` 地址 `10.255.0.13/24`
- 节点 `14`：板卡 `192.168.1.14`，本地 PC `192.168.1.24`，`rf0` 地址 `10.255.0.14/24`

用户态启动时会校验：

- 当前 `eth1` 地址是否能在节点表中找到自身。
- 每个 `pc_ip` 是否满足 `192.168.1.(10 + node_id)` 的驱动映射规则。
- `node_id`、`board_ip`、`pc_ip` 是否存在重复。

#### 2. 业务数据聚合与直发

- 默认最大聚合帧长度为 `640` 字节。
- 聚合魔数为 `AMPB`，版本号为 `1`。
- 第一个小包进入批次后，最多等待 `96 ms` 再看能否聚合更多小包。
- 若单个包长度超过 `640` 字节，则不参与聚合，直接单包发送。
- `ICMP Echo/Echo Reply` 默认走快速通道，尽量降低 `ping` 时延。

#### 3. 用户态止血版发送串行化

当前用户态发送侧包含以下止血版机制：

- 单独的发送线程 `amp_tx_thread` 负责真正调用 `write(amp_fd, ...)`。
- 业务数据和控制数据分别进入两个用户态队列。
- 控制队列优先于业务队列发送。
- 每次写完 `/dev/amp_ipi` 后增加一个很小的保护间隔，用于降低 TX 单槽被连续覆盖的概率。

#### 4. 网关与转发行为

用户态会在启动时做以下配置：

- 打开 `net.ipv4.ip_forward`
- 关闭 `rp_filter`
- 打开 `eth1` 上的 `proxy_arp`
- 拉起 `rf0`
- 设置 `rf0` MTU 为 `1600`
- 给 `rf0` 配置当前节点对应的 `10.255.0.x/24` 地址
- 为其他节点对应的 PC 地址配置 `proxy arp`
- 为其他节点对应的 PC 地址配置 `/32 -> rf0` 路由

## 协议与数据结构

### `amp_net_msg`

驱动和用户态共享同一套基础消息结构：

- `ip`：目标 IP 或返回数据的来源 IP
- `node_id`：目标节点号或来源节点号
- `len`：数据长度
- `data_type`：
  - `0` 表示业务数据
  - `1` 表示控制数据
- `data[]`：实际载荷，最大 `4096` 字节

### 控制帧

控制帧结构在驱动侧和用户态侧保持一致，包含：

- 帧头
- 帧类型
- 目的地址
- 帧序号
- 测试信号频率
- 测试信号使能
- 定频频率
- 组网数据发送测试
- 数据自回环
- 接收基带 IQ 对调
- 发射衰减系数
- 帧尾

控制帧头尾当前约定为：

- 帧头：`0xF00F`
- 帧尾：`0xE00E`

### `AMPB` 批帧

用户态业务聚合使用 `AMPB` 批帧格式：

- 魔数：`AMPB`
- 版本：`1`
- 标志位：当前固定为 `0`
- 子包数量：大端格式
- 批帧序号：大端格式
- 每个子包前带 `2` 字节大端长度字段

## 构建说明

### 用户态构建

进入 `amp_user/` 后执行：

```bash
cd amp_user
make
```

生成目标：

- `user_amp`

用户态 `Makefile` 当前默认使用交叉编译器：

- `arm-linux-gnueabihf-gcc`

并依赖：

- `pthread`
- `pcap`

### 驱动侧构建

驱动侧也提供了 `Makefile`，但它依赖外部环境：

- 目标内核源码树
- 交叉编译器
- 目标板匹配的内核配置与设备树

进入 `amp_driver/` 后可按 `Makefile` 中给定的 `KERNEL_SRC` 和 `CROSS_COMPILE` 进行模块构建，但这部分路径当前是针对特定环境写死的，使用前需要根据实际 BSP 调整。

## 运行前提

当前程序要在目标板上正常工作，至少需要满足以下条件：

- Linux 内核中启用了 TUN/TAP 支持。
- 系统中存在 `/dev/net/tun`。
- `eth1` 为有效数据接口，且配置了节点表中的板卡 IP。
- 驱动已正确加载并暴露 `/dev/amp_ipi`。
- CPU1 侧程序与当前共享内存地址、寄存器语义和 SGI 编号保持一致。
- 运行用户态程序时具备足够权限，以便执行抓包、配置 `sysctl`、创建 TUN、调整路由和邻居项。

## 当前限制与说明

- 仓库仅包含主控侧实现，不包含 CPU1 配套程序。
- 仓库不包含完整设备树节点与 BSP 集成内容。
- 当前节点表是静态三节点表，不是动态配置。
- 当前用户态默认只处理 IPv4 业务流。
- 当前止血版机制可以降低并发收发时的丢包概率，但由于共享 TX 区本质上仍是单槽语义，若 CPU1 侧没有配套 ACK 或更完整的队列协议，仍不能把高并发场景下的覆盖风险完全消除。
